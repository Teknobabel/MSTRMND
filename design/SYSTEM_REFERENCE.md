# Mastermind — system reference

This document describes the **current** architecture, data flow, and content model as of the repo state. Use it to stay consistent when adding features or content.

## Tech stack

- **Vite 6** + **TypeScript** (strict), ES modules.
- **Web UI**: DOM screens for menus (`index.html` + `src/navigation.ts`); **Canvas 2D** for the placeholder game view (`src/canvas/setup.ts`, `src/main.ts`).
- **Content**: JSON files under `content/`, validated with **Zod** in `src/game/contentSchema.ts` (issue-collecting pipeline; see **Content catalog pipeline**).
- **Validation CLI**: `npm run content:validate` runs `scripts/validate-content.ts` (Node + `tsx`; reports **every** issue in one pass). **`npm run typecheck`** runs `tsc --noEmit`. **`npm run build`** runs content validation, then typecheck, then `vite build`.
- **Tests**: **Vitest** (`npm test` / `npm run test:watch`); suites live next to sources as `src/game/*.test.ts` with shared fixtures in `src/game/testFixtures.ts` (`rawFixtureSlices`, `fixtureCatalog`, `seededRng`, `sequentialIds`).

## Content catalog pipeline

1. **Authoring**: Edit JSON under `content/`. Use stable string **`id`** fields for cross-references (lowercase slugs are typical).
2. **Loading (app)**: `loadContent()` in `loadContent.ts` static-imports every JSON file into a keyed **`RawContentSlices`** record (`{ traits, minions, agents, missions, locations, maps, assets, omegaPlans, lairs, events, organizationNames, playerProfiles, wantedLevels, balance }`) and calls **`parseCatalog(raw)`**. The slice list is defined once in **`CONTENT_MANIFEST`** (slice key → `content/<key>.json`); `scripts/validate-content.ts` iterates the same manifest. **`balance`** is a **single object**, not an array (see **Game balance**).
3. **Two validation phases** inside **`parseContentCatalog`** / **`parseCatalog`**:
   - **Shape phase** (**`parseContentSlices`**): each slice parsed **independently** against **`contentSliceSchemas[key]`** and normalized (e.g. `startingLevel` defaults to 1). A slice that fails shape is `null` in the result; its Zod errors become **`ContentIssue`** rows (`{ slice, entityId, path, message }`).
   - **Semantic phase** (**`collectContentIssues`**): array-level rules (duplicate ids, wanted-level ordering) plus the cross-slice reference checks — same logical dependencies as before: **traits** (defines `traitIds`) → **minions** (trait refs) → **agents** (same shape + trait refs; ids **disjoint** from minion template ids) → **assets** (defines `assetIds`) → **missions** (trait + asset refs + mission-effect placement rules) → **locations** → **`startingDynamicTraits` cross-check** on minion + agent templates → **maps** (location refs) → **omega plans** (mission refs + **`mapId`**) → **lairs** (mission refs + optional `startingAssets` asset refs; **`upgradeLevels`** ids unique across the ladder, disjoint from **`availableMissionIds`**, and never a **`coreMission`** template) → **events** (ids **disjoint** from mission template ids; required **`lifetimeTurns`** ≥ 1; optional **`minInfamy`** / **`minHeat`** gates 0–100; **both** requirement lists may be empty) → **wanted levels** (ordered heat tiers) → **balance** (`assetsPerLocationMin` ≤ `Max`; **`hireLevelInfamyThresholds`** strictly ascending; any minion **`startingLevel`** above `1 + thresholds.length` reported against the **minions** slice as unreachable by the hire pool). Checks whose inputs failed shape parsing are skipped; **all issues are collected**, never throw-on-first.
   - **`parseContentCatalog(raw)`** returns `{ catalog: ContentCatalog | null, issues: ContentIssue[] }` (`catalog` is null whenever issues exist). **`parseCatalog(raw)`** — used at boot and by the build gate — throws **`ContentValidationError`** whose message lists **every** issue. Content tooling should prefer the non-throwing form, the exported per-entity schemas (validate a single entity as it is edited), and **`collectContentIssues`** on a full draft catalog.

**Cross-reference rules** (enforced in `contentSchema.ts`):

- Minion `startingTraitIds` / `levelUpTraitOrder` → existing trait ids.
- Optional minion / agent **`startingDynamicTraits`**: each entry’s **`targetMinionTemplateId`** must reference an existing **minion** template id (not self); **`locationId`** must reference an existing location; no duplicate **`kind`+target** key; at most one positive bond (friend/ally) and one negative (rival/hatred) toward the same minion template; no **hero** and **wanted** for the same location on the same template.
- Agent templates (`content/agents.json`): same trait-reference rules as minions. **`challengeTraitIds`**, **`abilityIds`**, and **`movementBehavior`** are all **optional and independent** — an agent may carry all three, one, or none. What it *does* list is still checked: challenge traits must be known trait ids with no duplicates, and abilities must hold no duplicates. **`id`** must not collide with any **minion** template **`id`**.
- Mission **`requiredTraitIds`** → traits; **unique** per mission. Mission **`requiredAssetIds`** → assets; **duplicates allowed** (each occurrence needs one inventory unit). **`gain_assets`** **`assetIds`** and **`exchange_assets`** **`removeAssetIds`** / **`gainAssetIds`** → assets; **duplicates allowed** (multiset). **`exchange_assets`** must have at least one id across the two lists. **At least one** of `requiredTraitIds` or `requiredAssetIds` must be non-empty per mission. Missions with **`reveal_target_asset`** or **`steal_target_asset`** in **`onSuccessEffects`** / **`onFailureEffects`** must use **`targetType`** `asset_hidden` or `asset_revealed`. **`reveal_all_hidden_assets_at_location`**, **`steal_all_assets_at_location`**, **`steal_all_revealed_assets_at_location`**, **`security_level_delta`**, and **`intel_level_delta`** require **`targetType`** `location`, `asset_hidden`, or `asset_revealed`. **`add_target_minion_traits`** requires **`targetType`** `minion`; **`traitIds`** must reference existing traits and be **unique** within the effect (≥ 1 entry). **`add_random_participant_traits`** / **`add_all_participant_traits`** **`traitIds`** → existing traits, **unique** within the effect (≥ 1 entry). **`unlock_lair_mission`** may appear only in **`onSuccessEffects`** (not **`onFailureEffects`**); **`missionId`** must reference an existing mission template and must **not** be a mission on any lair's **`upgradeLevels`** ladder.
- Omega plan **`mapId`** → **`MapTemplate.id`**; omega plans parsed **after** maps.
- Omega plan stage `missionIds` (3×3 grid) → missions; **same mission id may repeat** within a plan. Stage **`requiredMissions`** is shape-validated to **1–3** (absent ⇒ **3**).
- **Lair** **`availableMissionIds`** and **`upgradeLevels[].missionIds`** → missions; no duplicate mission id within **`availableMissionIds`**; upgrade ids are unique across **all** of a lair's levels; the two are **disjoint** per lair; an upgrade id may not name a **`coreMission`** template (already unlocked at run start); **`startingAssets`** keys → asset ids. Issue paths read `upgradeLevels[i].missionIds[j]`.
- **Events** (`content/events.json`): **`EventTemplate`** extends **`MissionTemplate`** with a required **`lifetimeTurns`** (≥ 1 — turns the offer stays on the table), and optional draw-pool gates **`minInfamy`** / **`minHeat`** (0–100; absent or 0 ⇒ no gate). There is **no** separate expiry effect list: an offer that runs out of lifetime fires its **`onFailureEffects`** (**`unlock_lair_mission`** stays forbidden there, as on missions). **`id`** must not collide with any **mission** template **`id`**. **`requiredTraitIds`** / **`requiredAssetIds`** are validated like missions, but **both may be empty** (unlike missions, which require at least one non-empty requirement list). Effect placement rules match missions for target-dependent kinds.
- Map `locationIds` → locations; no duplicate location id **within the same map**; a location may appear on multiple maps.
- Asset ids unique in `assets.json`.
- **`organizationNames.json`**: JSON array of at least one non-empty string (no cross-references).
- **`wantedLevels`** (`content/wantedLevels.json`): ordered array of tiers (**`minHeat`** 0–100 strictly ascending, first tier **`minHeat === 0`**; tiers key off **heat**, not infamy), **`name`** (display), **`maxAgents`** (non-decreasing integers ≥ 0 — cap on opposing agents in play for that tier). Ordering rules enforced in **`collectContentIssues`**.

## Domain objects (catalog templates)

Enums in JSON are generally **lowercase** strings (e.g. trait `type`, location `locationType`).

### Traits (`content/traits.json`)

- **Trait**: `id`, `name`, `type`: `status_positive` | `status_negative` | `primary` | `secondary`.
- Passive definitions; minions, agents, and missions reference trait ids. **`status_positive`** / **`status_negative`** are excluded from per-location site/security rolls (see **Locations**). On missions, each participating minion’s trait list contributes flat success modifiers: **+10%** per **`status_positive`** occurrence and **−20%** per **`status_negative`** occurrence (summed across all participants), applied after the linear base % and clamped with the final result to **0–100**.
- **Minion pair affinity** (**`affinity.ts`**; state on **`GameState.minionAffinities`**): every **unordered** pair of roster minions shares **one** integer score starting at **0**. The score is **never surfaced in the game UI** — only the band it lands in. Bands, ascending: **Hated** → **Rivals** → **Neutral** → **Friends** → **Allies**. Thresholds and deltas are all tunable under **`balance.minionAffinity`**; defaults: Friends **+3**, Allies **+7**, Rivals **−3**, Hated **−7**, **hysteresis 2**.
  - **Deltas per resolve** (applied to every unordered pair of participants — **once per pair**, so a 3-minion crew moves 3 scores, not 6): lair/standard mission **±1**, global event **±2**, Omega plan mission **±2**, lair raid repelled **+3** (the raid overrides its `event` source; its failure delta is **0** because the run ends there). A solo mission has no pairs and changes nothing. Rows are stored with sorted instance ids so a pair has exactly one row; a pair with no row is Neutral at 0.
  - **Hysteresis**: a band is entered at its threshold but only given up once the score falls **`hysteresis`** further back (Friends earned at **+3** lapse only below **+1**), so a pair parked on a threshold cannot flip band every turn.
  - **Seeding**: designer **`startingDynamicTraits`** minion bonds seed the pair at that band’s own entry threshold once **both** minions are on the roster (**`seedStartingAffinities`**, re-run by `hireMinion` / `fireMinion` / `rehireMinion`); a score the run has already moved is never overwritten.
  - **Run-start spread** (**`rollStartingTemplateAffinities`**, stored on **`GameState.minionAffinitySeeds`**): the roster is **empty** at turn 1, so a run instead rolls a fixed table over the catalog’s minion **template** pairs and lands each entry on the real instance pair the first time both of those minions are hired (**`applyTemplatePairSeeds`**). One random pair opens already **Friends** (score in `[friendThreshold, allyThreshold − 1]` — never strong enough to open on Allies); one other opens already **Rivals** (mirrored into `[hatedThreshold + 1, rivalThreshold]`); **half** the remaining pairs (rounded down) get a non-zero score strictly inside the neutral band, so they lean without the player seeing anything; the rest start flat at **0**. Bounds are **derived from the thresholds**, not tuned separately, so retuning the track rescales the opening spread with it. Precedence at hire: designer bond → run-start seed → nothing, and any pair the run has already moved is left alone.
  - **Reporting**: pairs that cross a threshold during a resolve are logged as **`mission_completed.relationshipChanges`** and rendered in the mission result card’s **Relationships** group, the Turn Summary **Minions** section, and the Activity panel.
- **Minion-location affinity** (**`affinity.ts`**; state on **`GameState.minionLocationAffinities`**): every minion carries **one** hidden integer score **per location**, starting at **0**, moved only by missions at that site. Same machinery as the pair track with one threshold each way, since Hero and Wanted have no deeper tier: **Wanted** → **Neutral** → **Hero**. Tunable under **`balance.locationAffinity`**; defaults Hero **+3**, Wanted **−3**, **hysteresis 2**, **±1** per success/failure.
  - **Deltas per resolve**: every participant takes `missionSuccess` / `missionFailure` at **`getMissionTargetLocationId(am.target)`**. Missions with no site (**`minion`** / **`none`** targets) change nothing. Unlike the pair deltas these do **not** vary by mission source — a site is a site.
  - **Hysteresis**: a Hero earned at **+3** only lapses below **+1**; Wanted mirrors it. A single big swing can cross straight from Hero to Wanted.
  - **Run-start spread** (**`rollStartingTemplateLocationAffinities`**, stored on **`GameState.minionLocationAffinitySeeds`**): rolled over every (minion **template** × **run** location) slot — run locations, so a seed can never point at a site this run never plays. One random slot opens as a **Hero** (score in `[heroThreshold, heroThreshold + hysteresis]`), one other opens **Wanted** (mirrored), **half** the remaining slots (rounded down) get a non-zero score strictly inside the neutral band, and the rest start flat at **0**. Seeds land the moment the minion is hired — unlike a pair, a location needs no second party.
  - **Reporting**: crossings ride on **`mission_completed.standingChanges`** and render alongside relationship moves in the result card’s **Relationships** group, the Turn Summary **Minions** section, and the Activity panel.
- **Dynamic traits** (runtime only, not catalog `Trait` rows; stored on **`MinionInstance.dynamicTraits`**; see **`dynamicTrait.ts`**): kinds **`friend`** / **`ally`** / **`rival`** / **`hatred`** (toward another roster minion **`instanceId`**) and **`hero`** / **`wanted`** (toward a **`locationId`**). **Every kind is a read-only projection** of an affinity table — **`syncMinionDynamicTraits`** rebuilds the whole array from both tracks after every roster change and every resolve (which is what makes relationship pills symmetric); never edit them directly, and note that **nothing rolls dynamic traits any more**. Flat success modifiers: Friend **+5%**, Ally **+10%**, Rival **−5%**, Hatred **−10%** applied **once per unordered pair** on the mission (the mirror bond is skipped via **`pairKey`**), and Hero **+5%** / Wanted **−5%** **per minion** when the mission’s **`getMissionTargetLocationId`** matches. Designer optional **`startingDynamicTraits`** on **`MinionTemplate`** (see **Minions**) is validated in **`contentSchema.ts`** after locations load.

### Minions (`content/minions.json`)

- **MinionTemplate**: `id`, `name`, `description`, **`hireCommandPoints`** (integer ≥ 0; CP spent when hiring in the Main Phase), optional `startingTraitIds`, optional **`startingLevel`** (integer ≥ 1, default **1**; grants sequential traits from **`levelUpTraitOrder`** via the same rules as automatic level-ups until **`currentLevel`** reaches this value — **and** gates when the template may appear in the hire pool, see **Hire-pool infamy gate** under **Runtime game state**), `levelUpTraitOrder` (ordered trait ids for further level-ups), optional **`startingDynamicTraits`**: designer-authored opening relationships (`friend` \| `ally` \| `rival` \| `hatred` + **`targetMinionTemplateId`** — these **seed the pair affinity score**, not the instance, and only once both minions are hired — or `hero` \| `wanted` + **`locationId`**, which do land on the instance at hire; validated for refs, self-target, duplicates, and hero/wanted or positive/negative conflicts per **`contentSchema.ts`**).
- **MinionInstance** (runtime, not in JSON): **`instanceId`** (stable id for roster and missions), `templateId`, `currentLevel`, `currentExperience`, `traitIds`, **`dynamicTraits`** (array of **`DynamicTrait`** — relationship/location modifiers separate from catalog **`traitIds`**).
- **Creation** (`minion.ts`): `createMinionFromTemplate(template, instanceId, overrides?)` — callers supply `instanceId` (e.g. `crypto.randomUUID()`).
- **Mission XP & leveling** (`minion.ts` + **`executePlan`** in `gameState.ts`): when a mission **resolves** (duration reaches 0 with valid template and participants), **each participant** gains **`MINION_XP_PER_MISSION`** (**1**) XP. When **`currentExperience`** reaches **`MINION_XP_TO_LEVEL`** (**3**), the minion **levels up** (`currentLevel` +1), **`currentExperience` resets to 0**, and **`applyLevelUp`** runs: grant the **first** trait in `levelUpTraitOrder` the instance does **not** already have (if none left, level still increases but **no** new trait). A **`minion_leveled_up`** activity event is recorded for that turn (see **Activity log** below).
- **Manual / catalog level-up helpers** (`minion.ts`): `nextLevelUpTraitId`, `applyLevelUp`, `addTrait`, `removeTrait` — same ordered trait rule as automatic level-ups.
- **Hire availability** (`minion.ts`): **`templateStartingLevel`** (`startingLevel ?? 1`, floored at 1), **`maxHireableStartingLevel(infamy, thresholds)`**, and **`nextHireLevelInfamyThreshold`** (the UI's "next tier at N infamy" line). A template only enters the hire draw once **`player.infamy`** has unlocked its **`startingLevel`** — see **Hire-pool infamy gate** under **Runtime game state**.

### Agents (`content/agents.json`)

- **AgentTemplate**: **MinionTemplate**'s fields plus **`challengeTraitIds`**, **`abilityIds`**, and **`movementBehavior`** (`types.ts`). **`hireCommandPoints`** is validated like minions (often **`0`** for non-hirable opposition). Trait rules match minions. **All three agent-specific fields are optional and independent** — an agent with none of them is valid content: it occupies its site, counts toward the wanted-tier cap, and does nothing else.
- **`abilityIds`**: zero or more agent abilities, in **priority order** — when several *active* abilities could fire in one Agent Phase, the earliest usable one wins. See **Agent abilities** below.
- **`movementBehavior`**: which of the six movement rules this agent follows in the Agent Phase — see **Agent movement** below. **Optional**: an agent without one holds whatever site it is on for the whole run, which is how you author a fixture guarding one place.
- **`challengeTraitIds`**: the trait ids this agent brings as a **challenge** to every mission run at its location — see **Agent challenge traits** under **Missions** for the penalty maths. **Optional**: an agent with none poses no trait challenge, and is felt only through its abilities, its movement, or simply standing there. **`collectContentIssues`** flags an unknown trait id or a **duplicate** id in whatever list is authored. Authored in the editor's agent form (this list, `abilityIds`, and `movementBehavior` appear only for the **agents** slice).
- **`AgentInstance`**: **`MinionInstance`** plus **`catalogVisibility`** (`hidden` \| `revealed`, default **`hidden`** for spawns), **`challengeTraitIds`** and **`movementBehavior`** (both copied from the template at spawn), **`abilityIds`** (priority order preserved), **`deployedOnTurn`** (the turn it landed — it sits out *that* turn's Agent Phase, so a wanted-escalation spawn's placement means something), and **`huntedMinionInstanceId`** (`hunter` only — the minion it locked onto, `null` until it picks one). Not stored on **`PlayerState`**. Instances live on **`GameState.opposingAgentInstances`**; which location each belongs to is tracked in **`GameState.locationAgentPresence`** (see **Locations**). Location cards list **all** agents at the site for debug: **revealed** names plain, **hidden** names in parentheses.
- **Creation** (`agent.ts`): **`createAgentFromTemplate`** delegates to **`createMinionFromTemplate`** so leveling helpers in **`minion.ts`** apply unchanged when you spawn runtime agents later.
- **Lookup / spawn** (`agent.ts`): **`getAgentTemplateById`**, **`getOpposingAgentByInstanceId`**, **`getOpposingAgentsAtLocation`**, **`getRevealedOpposingAgentsAtLocation`** (subset helper), **`opposingAgentsAtLocationFromData`** (same lookup against loose rows mid-resolve), **`challengeTraitIdsForAgents`** (deduped, sorted challenge union — the success % input), **`countOpposingAgentsAtLocation`** / **`countOpposingAgentsAtLocationFromData`**, **`revealAllOpposingAgentsAtLocation`** (runtime reveal), **`spawnOpposingAgentsAfterWantedEscalation`** (wanted tier index must **increase** that resolve; fills toward **`maxOpposingAgentsForWantedIndex`** with random unused **`catalog.agents`** template and random playable **`locationId`** from the active omega map; new instances default to **`catalogVisibility: "hidden"`**).

#### Agent abilities (`agentAbility.ts`)

- Each agent template carries **zero or more** `abilityIds` (**`AgentAbilityId`**, authored per template in the editor). Two kinds, and the kind decides *when* it runs:
  - **Passive** — always in effect, a property of the site the agent is standing on. Fires inside **mission resolution**.
  - **Active** — spent. Using one **is** the agent's action for the Agent Phase, so an agent that acts does **not** also move that turn.
- **Hidden agents use both kinds exactly as revealed ones do.** Only the *reporting* is redacted (see below).

| Ability | Kind | Effect | Fires in |
| --- | --- | --- | --- |
| `brawler` | passive | Every participant of a **failed** mission at this site gains the `injured` trait (skipping any who already have it) | `executePlan`, after the template's failure effects |
| `investigator` | passive | A **failed** mission at this site adds `balance.agentInvestigatorFailureHeat` (default **5**) on top of the baseline failure heat | `executePlan`, with the baseline deltas |
| `guard` | passive | Security **cannot be reduced** at this site while the agent is present; raising it is never blocked | `applyMissionEffects` (`nextSecurityLevel`), covering targeted, global, and scoped security deltas alike |
| `security_chief` | active | Raises this site's security level by **1** | Agent Phase |
| `counterintelligence` | active | Reduces this site's intel level by **1** | Agent Phase |
| `asset_protection` | active | Flips one **revealed** asset slot at this site back to `hidden` | Agent Phase |

- **Site passives land once per mission**, however many agents at the site carry them — they are properties of the site, not per-head bonuses (`agentWithAbilityAtLocation` returns the first carrier, and that agent is the one named in the report).
- **An active only counts as spent when it would actually change something.** A Security Chief at a site already at its `locationLevel` cap, a Counterintelligence at a dark site, an Asset Protection with nothing in the open — each falls through to the next authored active, and then to **movement**, rather than wasting the turn.
- **Reporting**: every ability that fires logs an **`agent_ability_used`** activity row (`agentInstanceId`, `agentTemplateId`, `abilityId`, `locationId`, optional `assetId` for `asset_protection`, optional `activeMissionId` on passive triggers so the mission result card can group them). **`describeAgentAbilityUse`** in `turnReport.ts` renders it, naming the agent only when the player can see it (**`isOpposingAgentVisibleToPlayer`** at that site) and otherwise writing *"An unknown agent …"*. Unlike movement, an ability is **never** dropped from the report: the player always sees that their security jumped or their intel burned, just not always who did it.

#### The Agent Phase (`agentPhase.ts`, `executeAgentPhase`)

- **Its own step in the turn machine**: `main` → `executePlan` resolves missions and lands in **`agent`** → `executeAgentPhase` runs the opposition and lands in **`summary`**. The **Execute Plan** button runs both back to back, so the player sees one click, not two; a run that ends during resolution skips the phase entirely.
- The split is real, not cosmetic: `executeAgentPhase` reads **nothing but the state `executePlan` returned**, which is what makes it a separate step rather than a tail on the last one.
- **One action per agent**, in presence order: try each authored active ability in turn, and if none of them would change anything, move (see **Agent movement**). Agents whose `deployedOnTurn` equals the current turn sit the phase out completely — no ability, no move.
- Abilities resolve **before** movement, so the movement pass reads the world the abilities left behind (an Analyst will not chase intel a Counterintelligence just burned).

#### Agent movement (`agentMovement.ts`)

- **When**: in the **Agent Phase**, for every agent that did not spend its action on an active ability. Behaviors see this turn's failures, reveals, security bumps, and the Omega phase that just opened. Every such agent moves, **hidden or revealed**; agents deployed by this turn's wanted escalation sit it out (`deployedOnTurn`).
- **No pathfinding**: a run's map is an unordered set of sites (**`MapTemplate.locationIds`** has no adjacency or coordinates), so there is no "one step closer" to take. A behavior instead names its **attractors** — the sites it wants to be at (**`attractorLocationIds`**). The agent **holds position** when it is already standing on one, or when the behavior has nothing to chase this turn; otherwise it relocates to one of them in a single hop, chosen with the resolve **`rng`** when several tie. Movement never leaves the run's playable set.
- **Behaviors** (**`AgentMovementBehavior`**, authored per template in the editor — **optional**; an agent without one never moves):

| Behavior | Attractors | Nothing to chase when |
| --- | --- | --- |
| `defender` | Sites holding an asset the **active Omega phase's** missions list in **`requiredAssetIds`** (falls back to the whole plan when that phase needs no gear) | The plan needs no assets, or none are on the map |
| `investigator` | The site of the player's **most recent failed** mission (**`mostRecentFailedMissionLocationId`** — this resolve's events first, then back through **`activityLog`**) | No mission has failed at a **site** yet (`minion` / `none` targets leave no scene) |
| `hunter` | Wherever its quarry is **still working** after this resolve | It has no quarry, or the quarry is between jobs |
| `analyst` | The site(s) with the **highest `intelLevel`** | Every site is dark (intel 0 everywhere) |
| `asset_protector` | Sites with at least one **stored-`revealed`** occupied asset slot | Nothing is in the open |
| `opportunist` | Sites with the **lowest `securityLevel`** | Never — but a level map makes every site an attractor, so a parked agent stays put |

- **Hunter quarry**: kept on **`AgentInstance.huntedMinionInstanceId`**. The agent locks onto a random roster minion the first time it moves with a roster to choose from and **keeps** that quarry — it only re-picks once that minion leaves the roster, and holds `null` while the roster is empty. It follows the quarry to missions **still running** after this resolve; a mission that just finished is over and its crew is home.
- **Behaviors read the true world**, never the player-visible view: a hidden Analyst still knows which site the player has the best intel on.
- **Reporting**: each move logs an **`agent_moved`** activity event (`agentInstanceId`, `agentTemplateId`, `behavior`, `fromLocationId`, `toLocationId`) for **every** agent. Surfaces filter with **`isOpposingAgentMoveVisibleToPlayer`** (`intel.ts`): a move shows when the agent is **revealed**, or when **either end** of it is a site at intel **3**. Everything else stays out of the turn summary's **Sites** block and the Activity feed — an agent the player has never uncovered must not announce itself by moving.

### Missions (`content/missions.json`)

- **MissionTemplate**: `id`, `name`, `description`, **`targetType`**: `location` | `asset_hidden` | `asset_revealed` | `minion` | `none`, optional **`targetLocationTypes`** / **`targetLocationLevels`** / **`targetLocationIntelLevels`** / **`targetLocationSecurityLevels`** (**site filters** — see **Mission targets**), **`startCommandPoints`** (≥ 0), **`requiredTraitIds`** (unique trait ids; may be empty if assets carry the requirement), **`requiredAssetIds`** (catalog asset ids; **multiset** — duplicate ids mean multiple slots; each filled slot commits one matching unit from **`PlayerState.assets`** at **`assignMission`** and is stored on **`ActiveMission.plannedAssetIds`**), **`durationTurns`** (≥ 1), optional **`coreMission`** (boolean, default **false** when absent — designer-only, **never surfaced to the player**: a core mission is in the Lair **Missions** pool from turn 1 of every run **regardless of the lair picked**, on top of that lair's `availableMissionIds`; see **Lairs**), optional **`onSuccessEffects`** / **`onFailureEffects`**: arrays of **`MissionEffect`** (applied in order when a mission resolves; see **`missionEffects.ts`**). **`MissionEffect`** `kind` values: `reveal_target_asset`, `reveal_all_hidden_assets_at_location`, `steal_target_asset`, `steal_all_assets_at_location`, `steal_all_revealed_assets_at_location`, `unlock_lair_mission` (`missionId`), **`gain_assets`** (`assetIds`: multiset of catalog asset ids — duplicates grant multiple units), **`exchange_assets`** (`removeAssetIds`, `gainAssetIds`: multisets — removes up to inventory holdings per id, then grants gains), **`security_level_delta`** (`delta`: signed change to **`securityLevel`** at the mission location — negative reduces — clamped to **`[0, locationLevel]`**), **`security_level_delta_global`** (signed delta applied to **every playable location**, each clamped to **`[0, that location’s locationLevel]`**), **`security_level_delta_by_location_type`** / **`security_level_delta_by_location_level`** (same clamp semantics, filtered by **`locationType`** or **`locationLevel`**), **`intel_level_delta`** (`delta`: signed change to **`intelLevel`** at the mission location — negative reduces — clamped to **`[0, 3]`**; the surveillance lever, see **Site intel**), **`intel_level_delta_global`** / **`intel_level_delta_by_location_type`** / **`intel_level_delta_by_location_level`** (same clamp, scoped like their security twins — how **events** raise or lower intel without a target), **`reveal_hidden_assets_global`** / **`reveal_hidden_assets_by_location_type`** / **`reveal_hidden_assets_by_location_level`** (reveal up to **`count`** random **hidden occupied** asset slots in scope), **`remove_trait_from_all_minions`** (**`traitId`**), **`add_trait_to_random_minions`** (**`traitId`**, **`count`** — pool = full hired roster **including busy**), **`grant_command_points_next_turn`** (**`amount`** → **`pendingBonusCommandPoints`**), **`add_success_chance_modifier`** (**`delta`**, **`turns`** → **`activeSuccessModifiers`**), **`add_target_minion_traits`** (`traitIds`: unique catalog trait ids; grants any not-already-held to the **target minion** in **`player.minions`**; mission **`targetType`** must be `minion`), **`add_random_participant_traits`** (`traitIds`: unique catalog trait ids; grants any not-already-held to one participant chosen uniformly from **`participantInstanceIds`** using the resolve-phase RNG), **`add_all_participant_traits`** (same **`traitIds`** rules; grants any not-already-held to **every** participant in **`participantInstanceIds`**), `infamy_delta` (`amount`), `heat_delta` (`amount`), `max_concurrent_missions_delta`, `max_roster_size_delta`, `max_hire_offers_delta`, `max_participants_per_mission_delta`, `max_command_points_per_turn_delta` (each with signed integer **`delta`** except infamy). Baseline infamy (+5 success / 0 failure) and baseline heat (0 success / +5 failure) apply first, then effect deltas; **`infamy_delta`** / **`heat_delta`** effects **add**; both are clamped 0–100 at the end. **`orderedMissionEffects`** runs all **reveal** kinds first, then steal kinds (`steal_target_asset`, `steal_all_assets_at_location`, `steal_all_revealed_assets_at_location`), then the rest (including **`unlock_lair_mission`**, **`gain_assets`**, **`exchange_assets`**, **`security_level_delta`**, **`security_level_delta_global`**, scoped security deltas, hidden-asset reveals, **`add_target_minion_traits`**, **`add_random_participant_traits`**, **`add_all_participant_traits`**, roster trait sweeps, **`grant_command_points_next_turn`**, **`add_success_chance_modifier`**); **`steal_all_assets_at_location`** reveals hidden assets at the mission location then empties every occupied slot into inventory; **`steal_all_revealed_assets_at_location`** empties only **revealed** occupied slots; **`gain_assets`** adds to **`player.assets`** without changing locations; **`exchange_assets`** applies **`asset_lost`** / **`asset_gained`** for inventory changes; other steals leave **`empty`** slot(s). **`add_target_minion_traits`** appends each missing trait id to that minion's **`traitIds`** (no duplicates; ordering preserved); **`add_random_participant_traits`** does the same for one random roster minion in **`participantInstanceIds`**; **`add_all_participant_traits`** does the same for **all** of them; **`executePlan`** then syncs its participant lookup with updated minions so XP / level-up runs on top of new traits. **`unlock_lair_mission`** appends **`missionId`** to **`GameState.lairMissionIds`** if not already present (handled in **`executePlan`** after **`applyMissionEffects`**).
- **Success chance** (`mission.ts` + callers): **`successChancePercent(template, participants, options?)`** where **`MissionSuccessOptions`** may include **`additionalRequiredTraitIds`** (from **`missionSuccessOptionsForTarget`** in `gameState.ts`: site **required** traits + **revealed** security traits for the mission’s target location), **`playerAssets`** (inventory snapshot for the asset portion **only when** **`assignedAssetIds`** is omitted or its length does not match **`template.requiredAssetIds`**), **`assignedAssetIds`** (parallel to **`requiredAssetIds`**: each index is **`null`** or the matching catalog id; when provided with matching length, counts toward the base % instead of **`playerAssets`**), **`traitsCatalog`** (the parsed **`catalog.traits`** slice — when present, status trait modifiers apply), **`dynamicTraitDelta`** (flat sum from **`dynamicTraitSuccessModifierFromFullRoster`** in **`dynamicTrait.ts`**, using materialized pending template bonds against the full roster), **`eventSuccessModifierDelta`** (flat sum of **`delta`** from **`GameState.activeSuccessModifiers`** — timed modifiers from **`add_success_chance_modifier`**; each entry’s **`turnsRemaining`** decrements once per **`executePlan`**), and **`challengeTraitIds`** (the distinct challenge traits the site's opposing agents bring; each one **no participant holds** applies **−20%** after status, dynamic, and event modifiers). **Base %**: numerator = matched **distinct** required traits (participant union) + matched **asset slots** (either **`countMatchedAssignedSlots`** when **`assignedAssetIds`** matches length, else per-id `min(requiredCount, quantity)` from **`matchedAssetUnits`**); denominator = trait count + **asset occurrence count**; `Math.round(100 * matched / total)`; empty denominator → base **100%**. **Final %**: base plus **+10** per participating **`status_positive`** trait id on roster minions minus **20** per **`status_negative`** occurrence (each minion’s `traitIds` entry counts once per id), plus **`dynamicTraitDelta`**, plus **`eventSuccessModifierDelta`**, minus **20** × the count of **unmatched** challenge traits, then clamped to **0–100**. **Agent challenge traits** (see **Locations**): an agent template may list **`challengeTraitIds`** (optional — an agent with none adds nothing here). Every agent at the mission's site adds its challenge traits to that mission; the union is **deduped**, so two agents sharing a challenge cost the crew **once**. Each distinct challenge trait costs a flat **`balance.agentChallengeTraitPenalty`** (default **20**) unless **some participant** holds the matching trait — matching one only **avoids** the hit, it never raises the base %, because challenge traits are **not** part of the required-trait ratio. Only when the mission target maps to a **site** via **`getMissionTargetLocationId`** (location- or asset-targeted missions). **`executePlan`** collects challenges from **all** agents at that site (hidden + revealed) so the roll and **`mission_completed.successChancePercent`** reflect reality. **Plan / active mission UI** (`main.ts`) collects them only from the agents **visible to the player** (revealed by play, or any agent at a site with intel **3** — **`playerVisibleOpposingAgentsAtLocation`**) so opposition the player cannot see does not lower the **displayed** success %; the **Activity** line `roll … vs N%` shows the **true** resolve-time chance (including hidden agents and **dynamic** / **event** modifiers). **`minion`** / **`none`** targets have no challenge traits (no site location). Participants: 1–**`maxParticipantsPerMission`** minions for **lair** / **omega**; **event** missions use **1–3** fixed (see **Events**).

### Events (`content/events.json`)

- **`EventTemplate`**: Same fields as **`MissionTemplate`** (**site filters** included), plus a required **`lifetimeTurns`** (designer-set, ≥ 1) and optional **`minInfamy`** / **`minHeat`** draw-pool gates.
- **Ignoring an event costs what botching it costs.** There is **one** failure list, not two: **`onFailureEffects`** fires both when a started event mission **fails** and when an unstarted offer's **lifetime runs out**, so a designer writes the consequence of things going wrong in a single place. Expiry happens at the end of **`executePlan`** on the resolve where **`GameState.currentEventTurnsRemaining`** reaches **0** and the player never **started** the offer; starting it stops the countdown, and nothing fires while it is in flight. Expiry runs the list against a stub **`ActiveMission`** (no participants / no target) so participant-only and target-only effects are no-ops — an effect list shared with a real mission run must tolerate that. **`event_expired`** is logged whether or not the template lists any effects, so an offer never leaves the table silently. Ignoring an offer (no drag to Plan) is implicit — there is no Decline button.
- **Run opening**: the event slot starts **quiet** — `createInitialGameState` draws **no** offer and seeds **`eventCooldownTurnsRemaining`** with **`balance.firstEventTurn - 1`**, so the first offer is drawn at the resolve ending turn **`firstEventTurn - 1`** and is on the table for turn **`firstEventTurn`** (default **3**). Only **`firstEventTurn === 1`** puts an offer up at run start.
- **`special`**: optional marker for a **system-spawned** event (today only **`"lair_raid"`**). Special events are **never** in the random draw pool — the rule that owns them puts them on the table directly and overrides the event cooldown. **`collectContentIssues`** allows at most **one** **`lair_raid`** event. See **Lair Raid / game over**.
- **Draw pool**: **`eligibleEventTemplates(catalog, player)`** drops every **`special`** event, then keeps an ordinary event out of the rotation until **`player.infamy ≥ minInfamy`** and **`player.heat ≥ minHeat`** (either gate absent ⇒ always met), so harder events surface as a run escalates. Gates are read at draw time from the **post-resolve** player, so crossing a threshold opens that event for the next draw. When **nothing** is eligible the slot simply stays empty and the draw is retried at the following resolve — no cooldown is consumed and no **`event_rotated_in`** is logged.
- **Runtime offer**: the global event slot holds **one** event at a time in one of three states — **offer** on the table (**`currentEventTemplateId`** + **`currentEventTurnsRemaining`**), **in progress** (the player started it; the offer is cleared and its `ActiveMission` carries **`missionSource === "event"`**), or **cooldown** (**`eventCooldownTurnsRemaining`** quiet turns). Each **`executePlan`**: an unstarted offer loses one lifetime turn and **expires at 0**; a started offer leaves the table untouched; when the slot frees (expired, resolved, aborted, or the mission cancelled) a cooldown is rolled uniformly in **`[balance.eventCooldownTurnsMin, balance.eventCooldownTurnsMax]`** (**0–3** by default, **0** ⇒ the next offer appears that same resolve); otherwise a pending cooldown counts down and the next offer is drawn (uniformly, with replacement, over the **eligible pool**) when it reaches **0**. Nothing is drawn while an event mission is still running. **`event_rotated_in`** records the new id **and its `lifetimeTurns`** in the activity log.
- **Starting an event**: Assign with **`missionSource === "event"`**, **`missionTemplateId === currentEventTemplateId`**, **1–3** participants (ignores **`player.maxParticipantsPerMission`**), omega indices **`null`**. **`assignMission`** rejects a second event mission while one is active (**`invalid_mission_source_binding`**), and the **Events** tab stops offering the drag once one is running. Counts toward **`player.maxConcurrentMissions`**. Same **`ActiveMission`** pipeline as lair/omega for resolve, success %, and **`applyMissionEffects`**.
- **Timed success modifiers**: Effects **`add_success_chance_modifier`** push **`{ delta, turnsRemaining }`** onto **`GameState.activeSuccessModifiers`**. Each **`executePlan`** adds the total **`delta`** into resolve rolls and UI previews via **`eventSuccessModifierDelta`**, then decrements **`turnsRemaining`** and drops expired entries.
- **Bonus CP next turn**: **`grant_command_points_next_turn`** adds to **`player.pendingBonusCommandPoints`**; **`advanceToNextTurn`** sets **`commandPoints = maxCommandPoints + pendingBonusCommandPoints`**, then clears the bonus field.
- **Global / scoped effects**: **`security_level_delta_global`**, **`security_level_delta_by_location_type`**, **`security_level_delta_by_location_level`**, and the **`reveal_hidden_assets_*`** variants iterate **playable** locations from the active omega map; security deltas clamp per site to **`[0, locationLevel]`**. **`remove_trait_from_all_minions`** strips a trait id from every hired roster minion. **`add_trait_to_random_minions`** picks up to **`count`** distinct hired minions uniformly at random (**including minions busy on missions**), grants the trait if missing.

### Mission targets (runtime + planning UI)

- **`MissionTarget`** (runtime union in `types.ts`, stored on **`ActiveMission.target`**): `location` (`locationId`), `asset` (`locationId`, `slotIndex`, `visibilityAtAssign`), `minion` (`instanceId`), or `none`. Asset targets reference a **`LocationAssetSlot`** row at run time (by index into **`GameState.locationAssetSlots`** for that location).
- **Site filters** (`MissionTemplate` / `EventTemplate`, all optional) narrow **which sites** a mission may be aimed at, independently of which target **kind** it takes. Four dimensions, two authored and two per-run:
  - **`targetLocationTypes`** (`political` | `military` | `economic`) — the site's authored **`locationType`**.
  - **`targetLocationLevels`** (1 | 2 | 3) — the site's authored **`locationLevel`**.
  - **`targetLocationIntelLevels`** (0 | 1 | 2 | 3) — the player's **current** intel at the site (**`GameState.locationIntelStates`**, see **Site intel**).
  - **`targetLocationSecurityLevels`** (0 | 1 | 2 | 3) — the site's **current** security (**`GameState.locationSecurityStates`**). Security is capped per site at that location's **`locationLevel`**, so a filter naming only high values implicitly excludes sites that can never reach them.
- Each is a list; **absent or empty ⇒ that dimension is unrestricted**, a list admits **any** of its values, and all four are **ANDed** (`targetLocationTypes: ["military"]` + `targetLocationLevels: [3]` ⇒ level-3 military sites only). **`0` is a real value** for the per-run pair — "unscouted" / "unhardened" — not an absent filter. The two per-run filters read **live state**, so the same mission opens and closes sites as surveillance raises intel, events lower it, and resolved missions harden sites; they are checked when the mission is **started** and never call a mission in flight back. Filters only bite on a **location-resolving** `targetType` — `location`, `asset_hidden`, `asset_revealed` (**`missionTargetTypeTargetsLocation`** in `mission.ts`); on a `minion` / `none` mission they are dead authoring and **`collectContentIssues`** flags them, as it does duplicate entries within a list. Predicates live in `mission.ts`: **`missionAllowsTargetLocationType`**, **`missionAllowsTargetLocationLevel`**, **`missionAllowsTargetLocationIntel`**, **`missionAllowsTargetLocationSecurity`**, and the combined **`missionAllowsTargetLocation`**, which takes a **`MissionTargetSite`** (`location` + `intelLevel` + `securityLevel`) because two of the four are not catalog data. **`securityLevelForLocation`** (`locationCatalog.ts`) mirrors **`intelLevelForLocation`** as the shared reader.
- **`assignMission`** validates that the chosen **`MissionTarget`** matches the mission template’s **`targetType`** (see **`missionTargetMatchesTemplate`**), then — for a location- or asset-target — that the site clears **every site filter**, rejecting with **`target_location_type_not_allowed`** / **`target_location_level_not_allowed`** / **`target_location_intel_not_allowed`** / **`target_location_security_not_allowed`** (each carrying the offending site's value and the authored `allowed` list). **Location** and **asset** targets require a **playable** map location; **asset** also requires the slot to exist, to be **`occupied`** (not **`empty`**), and **`visibilityAtAssign`** to match the slot’s **effective** visibility — its stored visibility raised by site **intel** ≥ 2 (see **Site intel**). **Minion** targets must be a roster minion not on another mission and **not** among the participants. **`none`** skips target validation.
- **Security bump** on resolve: **`+1`** at **`getMissionTargetLocationId(am.target)`** when non-null, capped at **`maxSecurityLevelForLocation`** = that site’s authored **`locationLevel`** (1–3), not a global 3 for all sites. **Location**- and **asset**-targeted missions affect that asset’s **location**; **minion** / **none** do not change security by target (`raiseSecurityAfterMissionAtLocation` in **`gameState.ts`**). **`setLocationSecurityLevel(state, catalog, locationId, level)`** clamps security for future systems that lower heat; revealed security traits follow **`securityLevel`** (see **Runtime game state**).
- **Plan mission UI** (`main.ts`): **Mission** slot and **Target** slot can be filled in any order. The target **label** updates with the mission’s **`targetType`** (e.g. “Target Location”) and appends the mission's **site filters** when it has any (“Target Location — Military · Level 3 · Intel 2 or 3”); the same summary shows on the mission card as a **Target must be** row. Locations and assets whose site fails a filter are **refused on drop** (**`targetPayloadMatchesPlannedMission`** → **`locationPassesMissionFilters`**, which reads live intel / security), and swapping in a mission whose filters reject the staged target **clears** it (**`reconcileTargetWithMission`**). Because the per-run levels can move under a target staged on an earlier turn, **`syncAssignButtonState`** re-checks the filters and disables **Assign** with the requirement in its tooltip rather than letting the click fail. If **`targetType === "none"`**, the whole target field (**`#assign-target-field`**) is **hidden**. Dropping a mission that **mismatches** the staged target **clears** the target slot (**`reconcileTargetWithMission`**). **Asset** rows on location cards are **draggable chips** (per-slot identity) carrying the slot's **effective** visibility, so which slots can be targeted — and as `asset_hidden` or `asset_revealed` — follows that site's intel. Roster minion drags use JSON payloads. Putting a minion in **participants** clears the same minion from the **target** slot, and vice versa. When the planned mission has **`requiredAssetIds`**, a **Required Assets** fieldset lists one drop slot per occurrence; **Assets** panel cards drag with **`mastermind-asset-card`** JSON (type-matched slot only; **Available** counts subtract units already staged in the plan).

### Locations (`content/locations.json`)

- **LocationTemplate**: `id`, `name`, `description`, `locationType` (`political` | `military` | `economic`), **`locationLevel`** (1 | 2 | 3). Per-location **asset placement** is **not** in this JSON; at run start **`createInitialGameState`** assigns **1–3** random catalog assets per **playable** location on the active map (`LocationAssetSlot`: **`kind`** `occupied` with **`assetId`** + **`visibility`** `hidden` | `revealed`, or **`kind`** `empty` after a steal). **Every slot starts `hidden`** — the run's opening visibility comes from seeded **intel** instead (see **Site intel**).
- **LocationSecurityState** (runtime): `locationId`, **`securityLevel`** (`0` | `1` | `2` | `3`). New runs start at **`0`** via **`initialLocationSecurityStatesForLocations`**. Effective maximum per site is the location’s **`locationLevel`** (enforced when raising security). **During play**, each resolved mission at that site (via **`getMissionTargetLocationId`**) increments security by **1** up to that cap.
- **LocationIntelState** (runtime): `locationId`, **`intelLevel`** (`0` | `1` | `2` | `3`). Seeded per run by **`rollInitialLocationIntelStates`** (a few sites open above 0; see **Site intel**); the cap is a fixed **3** for every site (**`MAX_INTEL_LEVEL`**, structural — each level unlocks one specific kind of knowledge, so it is *not* a `BalanceConfig` knob). Moved by the **`intel_level_delta*`** mission effects (surveillance missions raise it; events raise or lower it). See **Site intel**.
- **Per-run site traits** (runtime, `GameState`): **`locationRequiredTraits`**: rolled at run start from **primary + secondary** traits only (excludes **`status_positive`** / **`status_negative`**) — level **1** → 0 traits, level **2** → 1, level **3** → 2. **`locationSecurityTraits`**: rolled stack of length **`locationLevel`** (reveal order = array order); only the first **`securityLevel`** entries merge into mission requirements (hidden entries do not). Both merge into **`missionSuccessOptionsForTarget`** for **location**/**asset** targets (see **`revealedSecurityTraitIds`**).
- **Opposing agents at sites** (runtime, `GameState`): **`locationAgentPresence`** lists **`AgentInstance.instanceId`** values per playable **`locationId`** (starts empty). Full **`AgentInstance`** rows live in **`opposingAgentInstances`** (each has **`catalogVisibility`**; spawns default **hidden**). Not authored in **`locations.json`**; **`spawnOpposingAgentsAfterWantedEscalation`** appends new ids to both when wanted escalates. **Locations** cards show an **Agents** row listing only the agents the player may see (**`catalogVisibility === "revealed"`** *or* site intel **3** — see **Site intel**); agents the player has not uncovered are omitted entirely rather than hinted at. Agents at the mission’s **target site** (same location id as **`getMissionTargetLocationId`**) press on it three ways, all of which count for **every** agent there, seen or not: their **challenge traits** are pooled against the crew (see **Agent challenge traits** under **Missions**), their **passive abilities** fire on the outcome, and their **Guard** passive refuses security reductions at that site (see **Agent abilities**). There is **no** flat per-agent success penalty and no critical-failure injury roll — an agent with no challenge traits and no abilities costs the mission nothing. When a mission with such a target **resolves**, every opposing agent at that site becomes **`revealed`** (success or failure). Outside mission resolution, agents act in the **Agent Phase** (see **The Agent Phase**).

### Site intel (`intel.ts`, runtime)

**`GameState.locationIntelStates`** holds one **`LocationIntelState`** per playable location (**`intelLevel`** `0`–`3`). Intel decides **what the player may see** at a site; it never changes the site itself, so the success roll, the agents' challenge traits and abilities, their Agent Phase decisions, and every other rule keep using the true state.

**Run start** (**`rollInitialLocationIntelStates`** in `locationCatalog.ts`): every asset slot on the map is generated **hidden**, and the player's opening leads come from intel alone — **`balance.initialIntelSitesAtOne`** (default **2**) random playable sites open at intel **1** and **`balance.initialIntelSitesAtTwo`** (default **1**) further sites open at intel **2**. Both tiers are drawn from the same pool **without replacement**, so the picks are distinct and no site can open above 2 (agents are never visible on turn 1). Every other site starts dark. This replaced the old **`initialRevealedAssetSlots`** pass, which flipped N random slots to `revealed` at run start.

| Intel | Unlocks |
|---|---|
| **0** | Nothing. Asset slots that are still `hidden` are **not listed at all** (the player cannot even count them); opposing agents are invisible. Anything uncovered **through other means** stays visible. |
| **1** | Every asset slot at the site is listed. Contents stay unknown — the row reads `Asset`. |
| **2** | Asset contents are identified, and the slots read as **revealed** for mission targeting too (see below). |
| **3** | Opposing agents at the site are visible, **including any that arrive later** while intel is still 3 — visibility is computed at read time, not stamped on the instance. |

- **Intel is a view, not a rewrite.** **`LocationAssetSlot.visibility`** and **`AgentInstance.catalogVisibility`** record what was uncovered *through other means* (reveal/steal effects, resolving a mission at the site) and are permanent; intel is layered on top via **`effectiveAssetSlotVisibility`** / **`isOpposingAgentVisibleToPlayer`**. That is what lets an event **lower** intel and actually cost the player information — knowledge granted only by intel goes away, knowledge earned by play does not.
- **Effective visibility is the visibility mission targeting uses.** At intel ≥ 2 a stored-`hidden` slot is a valid **`asset_revealed`** target (and no longer a valid **`asset_hidden`** one): **`assignMission`**, the plan-panel drop handler, the draggable asset chips, and **`steal_all_revealed_assets_at_location`** all go through `intel.ts` instead of reading `slot.visibility` directly. **`ActiveMission.visibilityAtAssign`** is fixed at assign time, so a later intel change never invalidates a mission already in flight.
- **UI reads player-visible counts**: the location card's **Intel level** row (tooltip lists the table above), the **Agents** row, the HUD **Agents** total (**`totalPlayerVisibleOpposingAgents`**), and the mission success **preview** (challenge traits gathered from **`playerVisibleOpposingAgentsAtLocation`**) — hidden opposition never moves the displayed chance, while the resolve roll still counts its challenge traits.
- **Changing intel**: the **`intel_level_delta`** family of mission effects (see **Missions**), or **`setLocationIntelLevel(state, locationId, level)`** in `gameState.ts` for other systems. Both clamp to `[0, MAX_INTEL_LEVEL]`.

### Maps (`content/maps.json`)

- **MapTemplate**: `id`, `name`, `description`, `locationIds` (ordered list of location ids).

### Assets (`content/assets.json`)

- **Asset**: `id`, `name`, optional `description`, optional **`supportAbility`**. Referenced by **missions** (`requiredAssetIds`), **lairs** (`startingAssets`), and **player inventory** **`PlayerState.assets`** (`Record<assetId, quantity>`). **Mission success %** uses **`assignedAssetIds`** on active missions (reserved inventory) or **`playerAssets`** when no per-slot list applies; the **Assets** panel shows **Available** (owned minus units staged in the plan mission UI — **required and support slots draw from the same pile**).

#### Support assets

- An asset carrying a **`supportAbility`** is a **support asset**: an *optional* extra the player drops into a mission's **support slots** on top of whatever the mission requires. Support assets are **spent on assign and consumed on resolve** exactly like required assets (refunded on cancel / abort), but they **never enter the required-trait / required-asset success ratio** — each one bends one rule of the resolve instead. An asset **without** an ability is inert cargo: still stealable, still valid as a `requiredAssetIds` entry or a `gain_assets` payout, but it cannot be placed in a support slot (**`not_a_support_asset`**).
- **`PlayerState.maxSupportAssets`** is how many fit on one mission. It starts at **`balance.startingMaxSupportAssets`** (default **1**; `0` turns the system off for the run) and is raised by the **`max_support_assets_delta`** mission effect — the lair-upgrade route. Floor **0**, not 1, unlike the other player caps. **`assignMission`** rejects an over-cap list with **`too_many_support_assets`**.
- **`ActiveMission.supportAssetIds`**: `string[]` (0–cap, in slot order). Unlike **`plannedAssetIds`** this is *not* aligned with anything on the template — any support asset fits any slot — so it holds ids only, with no `null` holes.
- The six abilities (**`SupportAssetAbility`** in `types.ts`). Two are read by **`computeSuccessChanceBreakdown`**; the other four are enforced in the resolve loop in `gameState.ts`, each by holding one dimension of the outcome to what the mission **found** rather than by skipping one specific rule — so a template effect cannot sneak past the promise the asset made:

| kind | What it does | Where |
| --- | --- | --- |
| `success_chance_bonus` | Flat `+percent` success. **Stacks** across slots; surfaces as **`SuccessChanceBreakdown.supportAssetDelta`** | `mission.ts` |
| `ignore_agent_challenge_traits` | The site's agents cost nothing: **`unmatchedChallengeTraitIds`** empties and the penalty is 0, however many are in play. The traits stay in **`challengeTraitIds`** with **`challengeTraitsIgnored: true`** so the UI can show what was shrugged off | `mission.ts` |
| `ignore_security_traits` | The target site's **revealed security** traits drop out of **`additionalRequiredTraitIds`** (**`missionSuccessOptionsForTarget`** takes the abilities). The site's own **`locationRequiredTraits`** are untouched — those are a property of the place, not of its guard posture | `gameState.ts` |
| `prevent_security_increase` | Security at the target site cannot end **higher** than it started: the automatic post-resolve bump is skipped **and** any net rise this mission's own effects caused there is given back. A **reduction** still stands. Agents at the site are still flushed into the open — this hides the traces, not the crew that watched | `gameState.ts` |
| `prevent_heat_increase` | `player.heat` cannot end higher than it started for this mission — baseline failure heat, the Investigator's bonus heat, and `heat_delta` effects all included. Reductions still land | `gameState.ts` |
| `prevent_injuries` | No participant comes home with an `injured` trait they did not already have. The **Brawler** does not fire at all (no misleading ability row in the report), and an injury a *template effect* granted is stripped afterwards | `gameState.ts` |

- Helpers live in `mission.ts`: **`isSupportAsset`**, **`supportAbilitiesForAssetIds`** (id list + catalog → abilities, skipping unknown / inert ids), **`hasSupportAbility`**, **`supportSuccessChanceBonus`**, **`describeSupportAssetAbility`** (the one-line player-facing gist used by cards and tooltips).
- **UI**: a **Support Assets** fieldset under Required Assets in the plan panel, one drop slot per open cap, filled by dragging any owned support asset card. The Assets panel marks support assets and states what they do; the active-mission card and the end-of-turn mission result list the committed ones. The **editor**'s asset form has a support-ability picker (with a `percent` row for `success_chance_bonus`).

### Lairs (`content/lairs.json`)

- **LairTemplate**: `id`, `name`, optional `description`, **`availableMissionIds`**, **`upgradeLevels`**, optional `cardArt`, optional **`startingAssets`** (`Record<assetId, quantity>` merged into **`PlayerState.assets`** at run start). **`GameState.activeLairId`** is chosen at random when **`catalog.lairs`** is non-empty (or taken from the title screen's pick).
- **`availableMissionIds`** — the lair's **standing** missions: **unlocked and assignable from turn 1**, shown under the Lair **Missions** tab, assigned with **`missionSource === "lair"`**. No duplicate ids per lair. **`lairMissionIds`** starts as this list followed by every mission template flagged **`coreMission`** that the lair does not already list (`initialLairMissionIds` in `gameState.ts` — so core missions are open from turn 1 in every run, including a run with no lair at all), and grows when **`unlock_lair_mission`** succeeds or via **`addLairMissionToPool`**.
- **`upgradeLevels`** — the lair's **upgrade ladder**: an ordered array of tiers, optional in JSON (default **[]**). Each **`LairUpgradeLevel`** is `{ optional name, optional minInfamy, missionIds }` with **at least one** mission id. A level's `missionIds` are **mutually exclusive**: the first of them to resolve **successfully** is installed, its siblings become unreachable for the rest of the run, and the ladder advances one rung. Levels are consumed in array order and **the player only ever sees the next open level** — earlier levels are settled, later levels are not shown at all.
- **`minInfamy`** on a level (0–100; absent or 0 ⇒ no gate) is the player **infamy** needed to **start** any of that level's missions. It gates **capability only, never visibility**: the level is shown in full as soon as it is the next open one, with the standing it wants spelled out, so a gated tier reads as a goal rather than a secret. Enforced in **`assignMission`** (**`lair_upgrade_infamy_locked`** carries `need` / `have`); helpers are **`lairUpgradeLevelMinInfamy`** / **`isLairUpgradeLevelUnlocked`** in `lair.ts`. Note this differs from the **event** `minInfamy`, which keeps a gated event *out of the draw pool* entirely.
- Ladder rules (all checked by **`collectContentIssues`**): every id must reference an existing mission; ids are **unique across the whole ladder** (a mission belongs to exactly one level of one lair); ids are **disjoint from `availableMissionIds`**; a **`coreMission`** template may not appear on a ladder (it is already unlocked at run start); and **`unlock_lair_mission`** may not target a ladder mission (upgrades are earned by climbing, not by being dropped into the pool).
- Legacy content: a lair with the pre-ladder flat **`upgradeMissionIds`** list and no `upgradeLevels` is migrated on parse to **one single-choice level per entry**, in list order (`normalizeLairUpgradeLevels` in `contentSchema.ts`). The editor writes `upgradeLevels` and drops the legacy key on the next save.
- **`completedLairUpgradeMissionIds`** (run state) lists the upgrades **installed** this run in completion order — at most one per level. It is what drives ladder position: a level counts as done when **any** of its `missionIds` is in that list, and the **current level** is the first one that is not.
- **End-of-turn report**, **Lair** section (`turnReport.ts`): installing an upgrade logs `Lair upgrade level N installed: <mission>`, then names the siblings it locked out for the run, then either the level that just opened or `Every lair upgrade level is installed.` A turn that carries infamy past the current level's **`minInfamy`** logs `Upgrade level N is now within reach — X infamy met.` The run-end **Organization** section reads `<lair> — X of Y upgrade levels installed`.

### Omega plans (`content/omegaPlans.json`)

- **OmegaPlanTemplate**: `id`, `name`, `description`, optional **`cardArt`** (rendered in the Omega Plan panel header **only when authored** — no default placeholder), **`mapId`** (must match **`MapTemplate.id`**), `stages` — exactly **3** stages, each with **`missionIds` of length 3** (fixed 3×3 grid) and **`requiredMissions`** (designer-authored **1–3**; **omitted in JSON means 3**, the legacy all-slots rule) — how many of that phase's missions must succeed before the phase clears. Win-path content only; **grid layout** is in JSON. Helpers in **`omegaPlan.ts`**: **`omegaStageRequiredMissions`** (clamped lookup), **`omegaPlanRequiredMissionTotal`**, **`isOmegaStageComplete`**. **Runtime progress** lives in **`GameState.omegaStageProgress`** (per-slot success flags for **all three** phases, `[stage][slot]`, never reset) plus **`activeOmegaStageIndex`**; **`executePlan`** marks each successful omega slot in **its own** phase row and advances the stage once the current row reaches **`requiredMissions`** (see **`gameState.ts`**). Clearing the **last** phase (**`stageAtExecute >= OMEGA_STAGE_COUNT - 1`**) is the run's **win condition** — see **Run endings**.
- **Victory copy**: optional **`victoryTitle`** (headline) and **`victoryNarrative`** (**`string[]`**, one paragraph per entry) are the **designer-authored ending** for that plan, shown on the victory modal when its final phase clears. This is the only authoring seam for how a run ends well — a plan without them falls back to generic generated copy, so every shipped plan should carry its own. Both shipped plans currently hold **`PLACEHOLDER — …`** prose to be replaced. Edited in the editor's Omega Plan form; read by **`buildRunEndReport`** in **`turnReport.ts`**, never by the rules engine.

### Organization names (`content/organizationNames.json`)

- JSON **array of strings** (each non-empty). At run start **`createInitialGameState`** picks one at random for **`GameState.organizationName`** (shown at the top of the controls panel). No ids or cross-references.

### Wanted levels (`content/wantedLevels.json`)

- **`WantedLevelTier`**: **`minHeat`** (inclusive floor on **`player.heat`**, 0–100), **`name`** (shown as **Wanted** in the HUD), **`maxAgents`** (cap on opposing agents placed on the map for that tier; **`executePlan`** may spawn up to this count when the tier index **increases** after resolve).
- Runtime **`GameState.wantedLevelTierIndex`** indexes **`catalog.wantedLevels`**; updated **once per **`executePlan`**** after all resolving missions have applied heat. **Never decreases** even if **`player.heat`** drops — with exactly one exception: **surviving the Lair Raid** stands the **top** tier down (see **Lair Raid / game over**). When the computed index is **greater** than the value at resolve start, **`spawnOpposingAgentsAfterWantedEscalation`** runs (see **`agent.ts`**).
- The **top** tier (**`topWantedTierIndex(catalog)`**, `null` when the catalog has fewer than two tiers) is the **loss trigger**: reaching it owes the player a **Lair Raid**. Shipped content puts it at **`minHeat` 100** — i.e. maxed heat.

### Game balance (`content/balance.json`)

**`BalanceConfig`** (`types.ts`) — a **single object** slice of designer-tunable knobs. Every field has a Zod **default** equal to the legacy constant (**`DEFAULT_BALANCE`** in `types.ts`, the single source for schema defaults and code fallbacks), so `{}` is a valid file that changes nothing. **All numeric gameplay constants quoted elsewhere in this document are these defaults** — the balance file overrides them. Parsed as `catalog.balance`; edited in the editor's **Game Balance** view (each field has a plain-language tooltip + hint).

| Knob (default) | Applied where |
|---|---|
| `statusPositiveBonus` (10) / `statusNegativePenalty` (20) / `agentChallengeTraitPenalty` (20) | `computeSuccessChanceBreakdown` via **`MissionSuccessOptions.balance`** (resolve + UI previews) |
| `dynamicTraitModifiers` (friend +5 / ally +10 / rival −5 / hatred −10 / hero +5 / wanted −5) | `dynamicTrait.ts` modifier functions (optional `modifiers` param; breakdown-from-roster reads `catalog.balance` itself); minion-to-minion kinds counted **once per pair** |
| `locationAffinity` — thresholds `heroThreshold` 3 / `wantedThreshold` −3 / `hysteresis` 2, deltas `missionSuccess` +1 / `missionFailure` −1 | `affinity.ts` (`nextStanding`, `locationAffinityDeltaForResolve`, `applyLocationAffinity`, `rollStartingTemplateLocationAffinities`); passed by `executePlan` and the hire/fire/rehire transitions |
| `minionAffinity` — thresholds `friendThreshold` 3 / `allyThreshold` 7 / `rivalThreshold` −3 / `hatedThreshold` −7 / `hysteresis` 2, deltas `missionSuccess` +1 / `missionFailure` −1 / `eventSuccess` +2 / `eventFailure` −2 / `omegaSuccess` +2 / `omegaFailure` −2 / `lairRaidSuccess` +3 / `lairRaidFailure` 0 | `affinity.ts` (`nextRelationship`, `affinityDeltaForResolve`, `applyMissionAffinity`, `seedStartingAffinities`); passed by `executePlan` and the hire/fire/rehire transitions |

| `startingMaxCommandPoints` (5), `startingMaxRosterSize` (5), `startingMaxHireOffers` (3), `startingMaxConcurrentMissions` (2), `startingMaxParticipantsPerMission` (3) | `PlayerState` init in `createInitialGameState` (mission effects still mutate the live values) |

| `assetsPerLocationMin`/`Max` (1/3) | `initializeLocationAssetPlacements` at run start (every slot starts **hidden**) |
| `initialIntelSitesAtOne` (2) / `initialIntelSitesAtTwo` (1) | `rollInitialLocationIntelStates` at run start (opening site visibility — see **Site intel**) |
| `securityGainPerResolvedMission` (1) | `raiseSecurityAfterMissionAtLocation` |
| `startingMaxSupportAssets` (1) | `PlayerState.maxSupportAssets` at run start (see **Support assets**) |

Semantic checks: `assetsPerLocationMin ≤ assetsPerLocationMax` and `eventCooldownTurnsMin ≤ eventCooldownTurnsMax` (in **`collectContentIssues`**). The old exported constants (`AGENT_CHALLENGE_TRAIT_PENALTY`, `MINION_XP_*`, `REROLL_HIRE_OFFERS_CP`, `EVENT_MAX_PARTICIPANTS_PER_MISSION`, `MINION_FIRE_REHIRE_COOLDOWN_TURNS`, `DYNAMIC_TRAIT_ROLL_PERCENT`) remain as **deprecated aliases of the defaults** — new code must read `catalog.balance`.

## Runtime game state (`src/game/gameState.ts`)

Not persisted in JSON; created per run via **`createInitialGameState(catalog, rng?, setup?)`** (requires **`ContentCatalog`** to roll initial hire offers; pass a seeded **`Rng`** for deterministic runs — defaults to `Math.random`). **`setup`** is the optional **`RunSetup`** (**`omegaPlanId`**, **`lairId`**) from the title screen's pickers: a field that is absent, **`null`**, or names an id the catalog does not have is rolled at random instead, and only the random path draws from `rng`. **`executePlan(state, catalog, rng, newInstanceId?)`** likewise accepts an id generator (default `crypto.randomUUID`) so resolves are fully deterministic under a seeded RNG (tests, future replays). **Resolution is simultaneous by design**: every mission resolving in one `executePlan` reads site required/security traits from the **start-of-turn snapshot**, so an earlier mission's security bump that resolve never changes a later mission's requirements (pinned by `gameState.test.ts`).

- **`TurnPhase`**: `main` | `resolve` | `agent` | `summary` — **`executePlan`** sets **`agent`** (missions are done, the opposition has not acted), **`executeAgentPhase`** then sets **`summary`** and the state **stays** there while the player reads the **end-of-turn report** (mission result modals, then the Turn Summary). Dismissing the Turn Summary is the only caller of **`advanceToNextTurn`**, which returns the player to **`main`** with **`commandPoints`** refilled and **`turnNumber`** incremented (still no separate **Next Turn** control). Everything gated on **`phase === "main"`** (Execute Plan, Cancel mission, hire, reroll) stays disabled underneath the report.
- **`PlayerState`**: `commandPoints` / `maxCommandPoints` (new game: 5/5; **`advanceToNextTurn`** sets `commandPoints = maxCommandPoints + pendingBonusCommandPoints`, then clears **`pendingBonusCommandPoints`** to **0**), `infamy` (0–100, clamped; the score the player raises — mission success grants +5), `heat` (0–100, clamped; law-enforcement attention the player keeps down — mission failure grants +5; the **only** input to the wanted level), `minions` (`MinionInstance[]`), `assets` (`Record<assetId, quantity>`), **`maxRosterSize`** (default **5**; hire blocked at cap), **`maxHireOffers`** (default **3**; cap on random offers per resolve), **`maxConcurrentMissions`** (default **2**; assign blocked when active mission count is at cap; may exceed current active count after a decrease until missions finish), **`maxParticipantsPerMission`** (default **3**; assign UI and **`canAssignParticipants`** cap for **non-event** missions), **`maxSupportAssets`** (default **1**, floor **0**; how many optional **support assets** ride along on one mission — see **Support assets**), **`pendingBonusCommandPoints`** (default **0**; one-shot CP added on top of **`maxCommandPoints`** at the next **`advanceToNextTurn`** after effects like **`grant_command_points_next_turn`**).
- **`GameState.wantedLevelTierIndex`**: index into **`catalog.wantedLevels`** (starts **0**). After **`executePlan`**, **`nextMonotonicWantedTierIndex`** sets **`max(previous index, tier implied by final `player.heat`)`** so escalation never rolls back when heat falls. If the new index is **greater** than the previous, opposing agents may spawn up to the new tier’s **`maxAgents`** (see **`spawnOpposingAgentsAfterWantedEscalation`**).
- **`GameState.organizationName`**: display string for the player’s evil organization, chosen once at **`createInitialGameState`** from **`catalog.organizationNames`**.
- **`GameState.activeOmegaPlanId`**: catalog **`OmegaPlanTemplate.id`** for this run, or **`null`** if **`catalog.omegaPlans`** is empty. Chosen once at **`createInitialGameState`** via **`resolveRunOmegaPlanId`** — the title screen's pick, or a random plan when that is **Random**. Shown in the **Omega Plan** panel (three phases, three missions each, names from mission templates). Defines the active **`mapId`** for location scope. **`GameState.activeOmegaStageIndex`** and **`omegaStageProgress`** track which omega **row** must be cleared next and which slots of every row have succeeded; **`executePlan`** sets a slot flag on the succeeding mission's own stage row and advances the stage once the current row has **`requiredMissions`** successes (fewer than three when the designer authored it that way).
- **`GameState.currentEventTemplateId`**: **`EventTemplate.id`** for the **offer on the table**, or **`null`** when there is none (empty catalog, the offer's mission is in progress, or the slot is cooling down). Drawn in **`executePlan`** via **`drawEventOffer`** (and at run start only when **`balance.firstEventTurn === 1`**). **`GameState.currentEventTurnsRemaining`**: lifetime turns left for that offer (from the template's **`lifetimeTurns`**); decremented per **`executePlan`**, and at **0** the offer expires, firing its **`onFailureEffects`**. **`GameState.eventCooldownTurnsRemaining`**: quiet turns before the next draw, rolled by **`rollEventCooldownTurns`**. Engagement is **derived**, not stored: an offer counts as started when an `ActiveMission` with **`missionSource === "event"`** exists at resolve time, so cancelling before Execute Plan leaves the offer (and its remaining lifetime) on the table, and **`assignMission`** rejects a second event mission while one is in progress.
- **`GameState.activeSuccessModifiers`**: `{ delta: number; turnsRemaining: number }[]` — flat **success %** addends from **`add_success_chance_modifier`**; total summed into resolve + UI as **`eventSuccessModifierDelta`**. Each **`executePlan`** decrements **`turnsRemaining`** and drops finished entries **after** an expiring offer's **`onFailureEffects`** apply.
- **Run endings** — **`GameState.runEnding`**: **`null`** while the run is alive; otherwise a **`RunEnding`**, one field rather than a pair of nullable flags so "won" and "lost" can never both be set.
  - **`{ kind: "victory"; omegaPlanId }`** — the active Omega Plan's **final** phase cleared this resolve (see **Omega plans**).
  - **`{ kind: "defeat"; reason }`** — the Lair Raid was lost; **`reason`** is **`GameOverReason`** (**`lair_raid_expired`** \| **`lair_raid_failed`**).

  **Victory wins ties**: a resolve that both finishes the plan and loses the raid is a **win** — the victory assignment is deliberately last and unconditional, and the raid-expiry branch only fires when **`runEnding === null`**. Once set, **`executePlan`** and **`advanceToNextTurn`** both refuse with the **`run_ended`** **`GameError`**, no further offer is drawn, and a terminal **`run_ended`** activity row is appended — the state is final.
- **Lair Raid**: the run's only loss condition, driven by the one catalog event marked **`special: "lair_raid"`** (**`lairRaidEventTemplate(catalog)`**; a catalog without one simply has no loss condition). **`GameState.lairRaidStatus`** tracks it: **`none`** → **`pending`** (the top wanted tier was reached and a raid is owed) → **`offered`** (it holds the event slot) → **`engaged`** (its mission is running). Each **`executePlan`**, in order: the resolve loop records the raid mission's outcome; the top-tier check arms **`pending`**; then the event slot places a **`pending`** raid on the **first free slot** — **overriding `eventCooldownTurnsRemaining`** and suppressing that resolve's ordinary draw — but never displacing an offer already on the table or an event mission in progress. **Losing** it (the offer's lifetime runs out unstarted, or its mission **fails**) sets **`runEnding`** to a **defeat**. **Surviving** it clears **`lairRaidStatus`** back to **`none`** and caps **`wantedLevelTierIndex`** at **`topWantedTierIndex - 1`** — the one break in the wanted ratchet — so the raid only returns once heat climbs back to the top tier's **`minHeat`**. The heat relief itself is **content**, not code: shipped **`evt_lair_raid`** carries **`heat_delta: -25`** in its **`onSuccessEffects`**. An **aborted** raid mission (invariant breach) requeues as **`pending`** rather than ending the run.
- **`GameState.activeLairId`** / **`lairMissionIds`** / **`completedLairUpgradeMissionIds`**: the title screen's lair pick at run start (a random one when that is **Random**, via **`resolveRunLairId`**) when **`catalog.lairs`** is non-empty; **`lairMissionIds`** is the pool for the Lair **Missions** tab (starts as **`availableMissionIds`** plus every **`coreMission`** template not already in it, deduped — `initialLairMissionIds`). **`completedLairUpgradeMissionIds`** lists the upgrades **installed** this run, at most one per level. Assigning from the lair allows **`missionTemplateId`** in **`lairMissionIds`** **or** in **`availableLairUpgradeMissionIds`** (the current level's choices only); a choice from a **later** level is rejected as **`mission_not_on_lair`**, a sibling of a choice already in flight is rejected as **`lair_upgrade_level_busy`** so two mutually exclusive upgrades can never resolve on the same tick, and a choice on a level whose **`minInfamy`** the player has not reached is rejected as **`lair_upgrade_infamy_locked`** (`need` / `have`) — the level stays visible either way.
- **`GameState.locationSecurityStates`**: one **`LocationSecurityState`** per **playable** location this run, initialized at security **`0`**. Shown in the **Locations** panel; **increments on mission resolution** when the resolved mission’s target maps to that location, capped by **`locationLevel`** (see **Locations**).
- **`GameState.locationIntelStates`**: one **`LocationIntelState`** per **playable** location, seeded at run start by **`rollInitialLocationIntelStates`** (**`initialIntelSitesAtOne`** sites at intel 1 + **`initialIntelSitesAtTwo`** more at intel 2, distinct picks; the rest at **`0`**). Gates the player-facing view of that site's assets and opposing agents; moved by the **`intel_level_delta*`** effects during `applyMissionEffects` and threaded back out of **`executePlan`** like the security states. See **Site intel**.
- **`GameState.locationRequiredTraits`** / **`locationSecurityTraits`**: `Record<locationId, string[]>` — rolled in **`createInitialGameState`** for playable locations only; merged into **`missionSuccessOptionsForTarget`** for mission success and UI when the target has a location id (**`revealedSecurityTraitIds`** applies the security stack slice).
- **`GameState.locationAssetSlots`**: **`LocationAssetPlacement[]`** (each **`locationId`** + **`slots`** of **`LocationAssetSlot`**). Initialized in **`createInitialGameState`** only for playable locations: each gets **1–3** distinct random **`catalog.assets`** ids (none if the asset catalog is empty); all slots start **occupied** and **hidden**, and nothing is revealed up front — opening visibility comes from seeded **intel** (see **Site intel**). The Locations panel shows label **Asset** with value **"Asset"** when the player knows only that the slot exists, catalog **name** once its contents are known, or **"—"** when **`empty`** — and **omits the row entirely** when site intel is 0 and the slot has not been revealed another way (see **Site intel**); in **Main Phase**, listed **occupied** rows are **draggable chips** for targeting, carrying their **effective** visibility (`main.ts`).
- **`GameState.opposingAgentInstances`** / **`locationAgentPresence`**: **`AgentInstance[]`** for all spawned opposing agents this run, plus one **`LocationAgentPresence`** row per playable location (**`agentInstanceIds`** empty at start). Each **`AgentInstance`** includes **`catalogVisibility`** (`hidden` \| `revealed`; spawns default **hidden**) and **`challengeTraitIds`** copied from its template. **`spawnOpposingAgentsAfterWantedEscalation`** (on wanted tier index increase) appends instances and presence entries; at most one opposing instance per **agent template** id at a time. Designers do not author placement in JSON. **`executePlan`** returns updated **`opposingAgentInstances`** every resolve (reveals at mission sites + tier spawns merge into the same locals).
- **Agent challenge traits at resolve**: **`executePlan`** builds the deduped challenge-trait union from **all** agents at **`getMissionTargetLocationId(am.target)`** (**`opposingAgentsAtLocationFromData`** + **`challengeTraitIdsForAgents`** in **`agent.ts`**) and passes it as **`MissionSuccessOptions.challengeTraitIds`**. Standing at a site is **not** itself a modifier: there is no flat per-agent success penalty and no critical-failure injury roll. Beyond challenge traits, an agent touches a mission only through its **passive abilities** (see **Agent abilities**). **`mission_completed`** logs **`challengeTraitIds`** and **`unmatchedChallengeTraitIds`** (both omitted when the site had no agents) for the activity panel and the turn report's **Fallout** group.
- **`GameState.availableMinionTemplateIds`**: template ids currently offered for hire, drawn by **`pickHireOfferTemplateIds`** (`gameState.ts`). Every draw excludes templates **already on the roster** and applies the **infamy level gate** (see below), then shuffles and cuts to **`maxHireOffers`**. Drawn at game start, at the end of each **`executePlan`** (using **post-resolve** infamy, so a mission that crosses a threshold widens that same draw), and on demand during **Main Phase** for **1 CP** (**`rerollHireOffers`**). Hiring removes that template id from the list for the rest of the phase until the next reroll. **`hireMinion`** only accepts ids in this list.
- **Hire-pool infamy gate**: **`balance.hireLevelInfamyThresholds`** (default **`[15, 35, 60, 85]`**) is an ascending list of infamy floors; **`maxHireableStartingLevel(infamy, thresholds)`** returns **`1 + (thresholds reached)`**, and only templates whose **`startingLevel`** is at or under that cap are drawn. Level 1 is always on offer, so rising **infamy** — the stat mission success builds — is what brings better recruits to the door. If the cap leaves **no** unhired template (every low-level one is already on the roster), the draw falls back to the **lowest `startingLevel` still unhired** rather than offering nothing. **`collectContentIssues`** rejects non-ascending thresholds and flags any minion whose **`startingLevel`** exceeds **`1 + thresholds.length`** as unreachable.
- **`ActiveMission`**: `id`, `missionTemplateId`, **`target`** (**`MissionTarget`**), **`missionSource`** (`lair` | `omega` | `event`), **`omegaStageIndex`** / **`omegaSlotIndex`** (set when source is omega; **`null`** for lair and event), `participantInstanceIds` (1–**`maxParticipantsPerMission`** for lair/omega; **1–3** for event), **`plannedAssetIds`** (aligned with template **`requiredAssetIds`** — `null` = empty slot at assign; non-null entries were deducted from **`player.assets`** at assign), **`supportAssetIds`** (0–**`maxSupportAssets`** optional **support assets**, deducted and refunded alongside `plannedAssetIds` — see **Support assets**), `turnsRemaining` (starts at `MissionTemplate.durationTurns`), **`startedOnTurn`**. Missions tick **only** when the player executes the plan: each active mission decrements `turnsRemaining`; at **0**, success is rolled vs **`successChancePercent`** with **`missionSuccessOptionsForTarget(state, target, supportAbilities)`**, **`supportAbilities`** from **`supportAbilitiesForAssetIds(am.supportAssetIds, catalog.assets)`**, **`assignedAssetIds: am.plannedAssetIds`** when the template lists required assets (otherwise **`playerAssets: player.assets`** for asset-only missions without slots), **`dynamicTraitDelta`** from **`dynamicTraitSuccessModifierFromFullRoster`**, **`eventSuccessModifierDelta`** from **`activeSuccessModifiers`**, **`challengeTraitIds`** from **all** agents at **`getMissionTargetLocationId(target)`** when set, plus **`traitsCatalog: catalog.traits`** (`mission.ts` + **`executePlan`** in **`gameState.ts`**); baseline infamy (+5 success / 0 failure) and baseline heat (0 success / +5 failure) are applied, then **`onSuccessEffects`** or **`onFailureEffects`** from the template via **`applyMissionEffects`** (**`missionEffects.ts`**), then **`applyLocationAffinity`** moves every participant’s standing at the mission’s site (optional **`mission_completed.standingChanges`**) and **`applyMissionAffinity`** moves every participant **pair**’s shared score (optional **`mission_completed.relationshipChanges`**), with **`syncMinionDynamicTraits`** re-projecting **`dynamicTraits`** from both tables afterwards. On **success**, **`executePlan`** also applies **`unlock_lair_mission`** entries (append to **`lairMissionIds`**) and, if the resolved mission is anywhere on the active lair’s **`upgradeLevels`** ladder (**`isLairUpgradeMission`**), appends it to **`completedLairUpgradeMissionIds`** — which installs it, retires its level, and opens the next one. **`mission_completed`** logs **`infamyDelta`** / **`heatDelta`** = total change for each (baseline + effect **`infamy_delta`** / **`heat_delta`** entries, clamped) plus **`baselineInfamyDelta`** / **`baselineHeatDelta`** and **`templateEffectDescriptions`** for the activity feed. The same tick applies **participant XP** (and possible **level-ups** + **`minion_leveled_up`** events), **+1 security** at the resolved target location when **`getMissionTargetLocationId(am.target)`** is set (per-location cap), **reveal all opposing agents at that location** when the target maps to a site and at least one agent is present, **`asset_gained`** when a steal effect fires, and **`mission_completed`** logging.
- **`GameState.minionAffinitySeeds`**: **`MinionTemplatePairAffinity[]`** — this run’s opening relationship spread, rolled once in **`createInitialGameState`** from the seeded `rng` and immutable thereafter (see **Minion pair affinity**).
- **`GameState.minionLocationAffinities`** / **`GameState.minionLocationAffinitySeeds`**: **`MinionLocationAffinity[]`** and **`MinionTemplateLocationAffinity[]`** — the Hero / Wanted track and its run-start spread (see **Minion-location affinity**).
- **`GameState.activityLog`**: **`TurnActivityEntry[]`** (each **`turnNumber`** + **`events`**). Main-phase actions append via **`appendActivityEvent`**; **`executePlan`** batches resolve outcomes with **`mergeResolveActivityEventsIntoActivityLog`**: **`mission_completed`** rows (with **`target: MissionTarget`**, optional **`challengeTraitIds`** / **`unmatchedChallengeTraitIds`**, optional **`relationshipChanges`**, optional **`standingChanges`**) plus any **`minion_leveled_up`** rows (and other **`ActivityEvent`** kinds as features grow). New turn buckets are **prepended** so the **Activity** panel shows **newest turn first**; the log is **not** cleared when the turn advances (session-only persistence until save/load exists). **`ActivityEvent`** union includes at least: `mission_completed`, `mission_started`, `mission_cancelled` (each carries **`target`**), **`mission_aborted`** (`activeMissionId`, `missionTemplateId`, `target`, `reason: "missing_template" | "invalid_participants"` — a resolving mission whose template or roster is invalid is **not silently dropped**: committed `plannedAssetIds` are refunded with `asset_gained` rows and this event is logged; should be unreachable today, exists so future systems fail loudly), `minion_hired`, `minion_rehired`, `minion_fired`, `minion_leveled_up` (`instanceId`, `templateId`, `newLevel`, optional `traitId`), **`agent_moved`** (`agentInstanceId`, `agentTemplateId`, `behavior`, `fromLocationId`, `toLocationId` — logged for **every** move, filtered to what the player can watch at render time), **`agent_ability_used`** (`agentInstanceId`, `agentTemplateId`, `abilityId`, `locationId`, optional `assetId`, optional `activeMissionId` on passive triggers — always shown, with the agent's name redacted when the player cannot see them), `asset_gained`, `asset_lost`, **`event_rotated_in`** (`eventTemplateId`, **`lifetimeTurns`**), **`event_expired`** (`eventTemplateId`, `effectDescriptions` — the template's **`onFailureEffects`**, empty when it lists none), **`run_ended`** (`ending: RunEnding` — terminal; no row is ever appended after it). **`asset_gained`**, **`asset_lost`**, and **`minion_leveled_up`** additionally carry an optional **`activeMissionId`**, stamped by **`executePlan`** when the row came out of one mission’s resolve so **`turnReport.ts`** can group each mission’s fallout under its own result card (rows from event expiry and Main-phase actions leave it unset).

Assignment rules: enforced in **`assignMission`** — **`missionTemplate.targetType`** must match the provided **`MissionTarget`**, and every authored **site filter** (**`targetLocationTypes`** / **`targetLocationLevels`** / **`targetLocationIntelLevels`** / **`targetLocationSecurityLevels`**) must admit the target's site; **playable** location scope for **location** / **asset** targets (**`activeLocationIds`**); **`missionSource`** **`lair`**: mission id must be in **`GameState.lairMissionIds`** **or** in **`availableLairUpgradeMissionIds`** (the active lair’s current upgrade level), no sibling of that level may already be running (**`lair_upgrade_level_busy`**), and **`player.infamy`** must meet that level’s **`minInfamy`** (**`lair_upgrade_infamy_locked`**); omega indices null; **`omega`**: active plan, **`activeOmegaStageIndex`**, and mission id must match **`omegaSlotMissionId`** for the chosen slot; **`event`**: **`missionTemplateId`** must equal **`currentEventTemplateId`**, omega indices null, **1–3** participants; sufficient **`startCommandPoints`**; participants not already on a mission; target minion not in participant list; **`activeMissions.length < maxConcurrentMissions`**; **`plannedAssetIds`** must match **`requiredAssetIds`** length, each non-null entry must equal that slot’s required id, and per-id tallies must not exceed **`player.assets`** (deducted on assign, logged as **`asset_lost`**; **`cancelMission`** refunds with **`asset_gained`**); **`supportAssetIds`** must be at most **`player.maxSupportAssets`** long (**`too_many_support_assets`**), every id must name a catalog asset carrying a **`supportAbility`** (**`not_a_support_asset`**), and its units are tallied against **`player.assets`** in the **same** pile as the required slots.

Cards are draggable only in the Main Phase, only while no sibling is running, and only once the infamy gate is met; draggable mission cards use **`missionSource === "lair"`** from either tab. The **Missions** menu renders the same offer under the heading `Lair Upgrades — Level N of M`. **Missions** panel (renamed from a single Active Mission column): **Active Missions** vs **Events** tabs — **Active Missions** lists all **`activeMissions`** with **Source** including **Event** for **`missionSource === "event"`**; **Events** shows only the draggable **current offer** with the turns left before it expires, or — when the slot is empty — whether an event mission is in progress or how many cooldown turns remain (in-progress event missions appear under **Active Missions**). Minion roster / hire cards and assign chips show **dynamic trait** pills in the same **Traits** row as catalog traits. The **Available to hire** section carries a **recruit-level line** under its heading (`Recruiting up to level N. Level N+1 recruits appear at X infamy (now Y).`, or `— every tier unlocked` at the top tier) so the infamy gate on the pool is visible rather than silent.
- **End-of-turn report** (`#overlay-turn-report` in `index.html`; controller + rendering in `main.ts`, data in **`src/game/turnReport.ts`**): **Execute Plan** dispatches **`executePlan`** and then **`executeAgentPhase`** (one click, two phases — a run that ended during resolution skips the second), leaving the state in the **`summary`** phase, then calls **`buildTurnReport(before, after, catalog)`** and opens the overlay. The report is a sequence of steps — one **Mission Result** modal per mission that finished this resolve (mission art, description, source, target, roll vs the true success %, duration, committed assets, participating minion chips, and the grouped effects of that outcome: **Standing** infamy/heat, **Success/Failure effects**, **Assets**, **Minions**, **Fallout** naming each **agent challenge trait** on site, whether the crew covered it, and any **passive agent ability** that fired on that mission), a dedicated **Agents** summary block carrying every **ability use** (agent redacted when unseen) followed by the **movement** the player could watch, with deployments and identifications staying in **Sites**, followed by a single **Turn Summary** modal listing every section the diff produced. **Continue** advances one step; **Skip all** (shown only while more than one mission card is still queued) jumps straight to the summary; the summary’s **Begin turn N+1** dismisses the overlay and dispatches **`advanceToNextTurn`**. A resolve with no finished missions opens straight on the Turn Summary. Aborted missions (**`mission_aborted`**) get their own card rather than vanishing. Report lines carry a **`good`** / **`bad`** / **`neutral`** tone that drives the colour and the ▲ / ▼ marker; nothing in `turnReport.ts` touches the DOM, so the whole report is unit-tested in `turnReport.test.ts`.
- **Run-end overlay** (`#overlay-run-end` in `index.html`; controller in `main.ts`, data from **`buildRunEndReport(state, catalog, ending)`** in **`src/game/turnReport.ts`**): when **`executePlan`** returns a state with **`runEnding`** set, **Execute Plan** **skips the mission recap and Turn Summary entirely** and opens this overlay instead — the same two-step flow whether the run was **won** or **lost**. Step 1 is the outcome modal: on a **win**, the completed plan's **`victoryTitle`** as the headline and its **`victoryNarrative`** paragraphs as the body (verdict chip *Omega Complete*); on a **loss**, **Game Over** with generated prose (verdict *Overrun* for an expired raid, *Captured* for a lost one). Step 2 is the **Run Summary** (**Final standing**, **Omega Plan**, **Career** tallies read from the whole **`activityLog`**, **Organization**) — the same sections either way, with wording and tone switched on the ending. It reuses the `turn-report-*` shell with a `run-end-*` skin and sits **above** the turn report (`z-index: 7`); the overlay carries **`run-end-overlay--victory`** on a win, which recolours the shell **gold** instead of the house red. Dismissing the last step **rolls a fresh run** (**`createInitialGameState`** with the title screen's current picks) and returns to the title screen via **`NavigationApi.returnToMainMenu()`**, so **Play** starts over rather than dropping the player back into a dead state.
- **Run setup** (`#select-omega-plan` / `#select-lair` on the title screen; controller in **`src/ui/runSetup.ts`**): **`initRunSetup(catalog)`** fills each picker with **Random** plus one option per catalog **`OmegaPlanTemplate`** / **`LairTemplate`** (catalog order, both defaulting to **Random**) and returns **`read()`** → **`RunSetup`** (**`null`** on a field left **Random**). **Play** fires **`NavigationHooks.startRun`**, which rolls a fresh run through **`createInitialGameState(content, undefined, runSetup.read())`**, so the picks apply to that run and to every later one without a reload. The run-end overlay's dismissal re-rolls through the same path. **Play always begins a new run**, so leaving the game with the pause overlay's **Quit** abandons the run in progress rather than parking it.
- `navigation.ts` wires visibility and **starts/stops** the canvas RAF loop when the game screen is visible and not paused. **`initNavigation`** takes **`startRun`** alongside **`setGameLoopRunning`** and returns a **`NavigationApi`** (**`returnToMainMenu()`**), passed into **`initGameController`** so a finished run can leave the game screen. Because the controller needs the api and the api needs the controller's **`startRun`**, `main.ts` routes Play through a ref it fills in as soon as **`initGameController`** returns.
- Canvas draws a placeholder “Game” label; rules and economy are driven from the DOM panel, not the canvas.

## Content editor (dev-only)

Open **`http://localhost:5173/editor.html`** while `npm run dev` is running. Vanilla-TS app under **`src/editor/`**; it is **never bundled into production builds** (Vite's build input is `index.html` only, and the API plugin is `apply: "serve"`).

- **Dev API** (plugin in `vite.config.ts`): `GET /__content-api/slices` reads every `CONTENT_MANIFEST` file; `PUT /__content-api/slices` re-runs **`parseContentCatalog`** on the whole draft and **refuses to write when issues exist** (422 with the `ContentIssue[]`), so files on disk always pass the build gate. Writes go through **`serializeContentSlice`** and only touch changed slices. **The first save canonicalizes formatting of every content file once**; after that, diffs are minimal. Saving triggers HMR on the game page (live preview loop). **Art uploads**: `GET /__content-api/art` lists `public/assets/cards/custom/*.webp` (name, path, animated flag); `POST /__content-api/art?name=<slug>[&overwrite=1]` takes raw WebP bytes — filename is slugged, magic bytes verified (a renamed PNG is rejected), ≤ 8 MB, existing file → 409 unless overwriting. Shared pure helpers (slug + `RIFF…WEBP` + `ANIM`-chunk detection) live in **`src/editor/artFiles.ts`** (browser-safe; used by both the plugin and the editor page; unit-tested). Uploads live under `public/`, so Vite serves them in dev, copies them into `dist/` on build, and they are committed to git beside the content that references them.
- **Draft model** (`src/editor/store.ts`): in-memory copy of all raw slices; every edit snapshots (undo, depth 50), re-validates with the real schema pipeline, and mirrors to `localStorage` (restore prompt after an accidental tab close). Invalid work-in-progress lives in the draft, never on disk.
- **Layout** (`src/editor/main.ts`): slice sidebar (issue-count badges) → entity list (`+ New`, per-entity issue dots) → detail form → global issues panel (click an issue to jump to the entity). Header: **Save** (disabled while issues exist), **Undo**, **Unreferenced…** report, status.
- **Forms** (`src/editor/forms/`): hand-written per slice. Every cross-reference field is an **id picker** over the current draft. Fixed-vocabulary multi-selects use **`checkboxGroup`** (`widgets.ts`) — a row of checkboxes that commits in option order; the mission / event form uses it for the four **site filters** (`targetLocationTypes`, `targetLocationLevels`, `targetLocationIntelLevels`, `targetLocationSecurityLevels`), which stay visible on a non-location `targetType` with a hint that they are inert, so stale values are never hidden from the designer. The **Game Balance** view (`balanceForm.ts`) is a singleton form (no entity list / New / Duplicate / Delete / Rename): grouped fieldsets for every scalar `BalanceConfig` knob, each with a **plain-language tooltip + hint** explaining its gameplay effect, plus a live **formula strip** showing the success-chance formula with the draft's current numbers. Three knobs are **not** scalars and get hand-rolled blocks: **`dynamicTraitModifiers`** (nested object, one row per bond kind), **`minionAffinity`** and **`locationAffinity`** (nested objects — each gets a thresholds fieldset with a live **track strip** showing every band’s entry point and where it lapses under the current hysteresis; `minionAffinity` adds a per-resolve deltas fieldset) and **`hireLevelInfamyThresholds`** (ascending list — a `listEditor` of `Level N at infamy …` rows with add/reorder/remove, plus a summary strip of the resulting infamy → level ladder). Missions/events share one form with a **Core Mission** checkbox under `durationTurns` (missions only — events are drawn from their own pool; unchecked drops the key from the JSON), the **effects list editor** (kind-specific fields per `MissionEffect`; kinds incompatible with the current `targetType` are disabled via **`effectKindTargetTypeRequirement`**; a note shows the `orderedMissionEffects` resolution order) and a **success-chance preview** (pick up to 3 minion templates; real `computeSuccessChanceBreakdown`). Omega plans render the literal 3×3 mission grid, each stage row carrying a **must complete N of 3** number input for that phase's **`requiredMissions`**. Minions/agents include a `startingDynamicTraits` sub-editor. Inputs commit on `change` (blur/enter), not per keystroke. Every art-path field (`cardArt` on minions, agents, missions, events, locations, assets, lairs, omega plans; `profilePic` on player profiles) uses the **art field widget** (`src/editor/artField.ts`): live thumbnail preview with an **animated ✓ / static webp / file not found** badge, editable path input, **Upload .webp…** (client-side preflight, name prompt seeded `<slice>-<id>`, overwrite confirm on 409), and a picker over previously uploaded files. **Traits, wanted levels, maps, and organization names intentionally have no art fields.**
- **Tools**: **Rename id…** (uses `applyIdRenameRaw`, updates all referents), **Duplicate** (`-copy` id suffix), **Delete…** with reference-impact modal (`referencesTo` over the draft), **Unreferenced…** report (`unreferencedIds`; caveat shown that unreferenced ≠ unused — some content is only rolled/offered at runtime).
- Entity **id fields are read-only** in forms — ids change only through Rename so references can never silently dangle. New entities prompt for their id.

## Conventions

- **Adding a catalog slice**: add the key to **`CONTENT_SLICE_KEYS`** (drives **`CONTENT_MANIFEST`**, `RawContentSlices`, and the validator CLI), an entity schema + entry in **`contentSliceSchemas`**, a normalizer in **`parseContentSlices`**, semantic checks in **`collectContentIssues`**, the field on **`ContentCatalog`**, the static import in `loadContent.ts`, and (if it holds id references) the walkers in `contentRefs.ts`.
- Report content problems as **`ContentIssue`** rows (accumulate; never throw on the first problem inside the schema layer). Only `parseCatalog` throws, and it throws everything at once.
- Any tool that **writes** `content/*.json` must serialize through **`serializeContentSlice`** so diffs stay canonical.
- **Card art paths** (`cardArt` / `profilePic`) are site-root paths to files under `public/` (uploads go to `public/assets/cards/custom/`, WebP only — animated WebP plays natively in the plain `<img>` from `createCardArtImg`, no code needed). `scripts/validate-content.ts` fails the build when a referenced art file does not exist on disk (Node-only check; the browser schema validates the string shape only).
- Keep **designer data** in `content/*.json` and **runtime/progression** in **`gameState.ts`** and related TS modules (`types.ts`, `minion.ts`, `agent.ts`, `wantedLevel.ts`, `mission.ts`).
- After editing JSON, run **`npm run content:validate`** (or `npm run build`) before assuming content is valid. After editing rules-engine code, run **`npm test`** and **`npm run typecheck`** (the build runs both validation and typecheck; Vite alone does not typecheck).
- Rules-engine functions take an injected **`Rng`** (and an id generator where they mint instances) — never call `Math.random` / `crypto.randomUUID` directly inside `src/game/`.
- **New gameplay constants go in `BalanceConfig`**, not as code literals: add the field + default to `DEFAULT_BALANCE` (`types.ts`), the schema field in `balanceConfigSchema`, thread it from `catalog.balance`, and add the row (label + plain-language tooltip) to the editor's `balanceForm.ts`. A **non-scalar** knob (array or nested object) must also be excluded from that file's **`ScalarKey`** union and rendered by its own block — the generic `numberInput` loop only handles numbers.
- UI event handlers in `main.ts` route state transitions through **`dispatch`** rather than assigning `state` themselves.
